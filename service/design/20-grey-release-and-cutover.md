# 数据迁移与启用方案

## 目标与边界

当前没有实际用户，不设计租户灰度、双写、长观察窗口和自动回切。迁移的唯一硬约束是不可再生数据不丢失。MyTools、DownloadBot 和 MsgService 的旧代码与旧数据库在迁移验收前保持不变；新服务使用独立 schema，确认数据完整后直接启用新入口。

历史媒体迁移完成后，使用 `service/scripts/media_migration_gate.py` 离线校验快照、Asset Registry dry-run/正式报告、Media Library dry-run/正式报告以及两个目标对账报告。门禁要求来源记录和来源标签数量覆盖旧快照；媒体项、资产数允许因内容去重少于旧记录数。

## 数据分类

- 必须保留：账号、权限、用户配置、书架、阅读进度、书签、消息正文与附件关系、业务资产关系，以及仍需继续处理的业务状态。
- 可以重新生成：任务执行历史、搜索结果、缓存、远端文件索引、媒体标签、缩略图、截图、简介和其他派生索引。
- 无法转换的记录不得静默丢弃。迁移报告至少记录来源主键、失败原因和建议处理方式；必要时保留旧表只读查询。

## 最小迁移流程

1. 备份旧数据库，并记录备份文件、时间和恢复命令。
   使用 `service/scripts/legacy_data_retention_gate.py` 校验逐表行数、备份摘要和恢复读取结果；详细分类见 `23-legacy-data-disposition.md`。
2. 创建各服务独立 schema，执行 Flyway，不修改或删除旧表。
3. 对必须保留的数据执行一次可重复运行的导入。导入使用稳定旧主键或业务键保证幂等。
4. 比较来源数、成功数、跳过数和失败数；失败记录导出后修正并重跑。
5. 对可再生数据按需创建重建任务，不要求迁移旧任务历史。
6. 核心查询抽样正确后启用新入口；确认新服务稳定前保留旧库和旧服务目录。

## 验收条件

- 必须保留的数据满足 `来源数 = 成功数 + 已存在数 + 失败数`，且失败数最终为零或已有人工确认的保留方案。
- 关键外键关系可解析，不存在孤立的书架、进度、附件或资产关系。
- 迁移脚本同参数重跑不会产生重复数据。
- 新服务能够查询迁移后的核心数据，并能创建、查询和取消异步任务。
- 旧数据库备份已验证可读取；迁移完成前不删除旧库、旧文件或原始附件。

## 简化原则

仓库中已有的预检和迁移证据工具可以按需使用，但不作为当前启用门禁。只有在未来出现真实用户、持续写入或零停机要求时，才补充双写、按租户灰度、差异对账和自动回退设计。
