## ⚠️ 第 4 条：我按"保持现状"执行，但必须把这个隐患写清

**D1 的现象**：`SET epoch = epoch + 1, catalog_version = CONCAT('catalog-', epoch + 1)`
在 **MySQL 从左到右求值**（用到已更新的 epoch ✓）→ 首次发布得 `catalog-2`/`epoch=1` ✓；
**H2 得 `catalog-1`** ✗。

**保持现状的代价**：**单元测试跑在 H2 上，所以测试看到的版本名与生产不一致** ✗ ✓ ——
这**正是本会话前几个真缺陷的成因类型** ✗（V5/V6 列宽就是"**H2 不强制 VARCHAR 宽度**"掩盖的 ✓，
`order` 的 0/1 基差异也是同类 ✓）。

**所以这条虽然"保持"，但我建议你留一个心眼** ✓：**凡是用 H2 验证过的"版本号/顺序/长度"类断言，
都不要当作生产行为** ✗ ✓ —— 需要时用真实 MySQL 复核（本会话已建立隔离容器与复核脚本 ✓）。

**若将来要修**，需要的仍是一个**数据迁移决策** ✓（是否重命名/回填历史 `catalog_version` ✓），
因为改法会让已有库产出**重名版本** ✗ —— **这也是它当时被列为"待拍板"而不是"直接修"的原因** ✓。
