## 4. `catalog_version` 的 MySQL/H2 语义差（D1）✗

`SET epoch = epoch + 1, catalog_version = CONCAT('catalog-', epoch + 1)` 在 MySQL 里**从左到右求值**（用到已更新的 epoch）✓
→ 首次发布得 `catalog-2`/`epoch=1` ✓；**H2 得 `catalog-1`** ✗。

设计第 391-392 行的示例里**两者同数** ✓。**修法会让已有 `catalog-<epoch+1>` 的库产出重名版本** ✗
→ **需一个数据迁移决策** ✓（要不要重命名/回填历史版本号 ✗）。

## 5. `changeNote` 的 200 字符上限（第 152 轮由实现者主动标出）✗

实现者把摘要截断到 **200 字符** 后写进审计 `summary` ✓，理由是与前端 `CHANGE_NOTE_MAX_LENGTH` 一致 ✓，
且**保证 `summary VARCHAR(512)` 一定写得下** ✓ —— 但**它自己指出：这不是设计条款** ✗ ✓。

| 选项 | 后果 |
| --- | --- |
| 保持 200 截断 | 超长摘要**静默丢失尾部** ✗ —— 用户填了 300 字，只存 200 ✗ |
| 不截断、靠 `VARCHAR(512)` | 超过 512 字符会**写库失败**（MySQL 报错 ✗），比静默截断更显眼 ✓ |
| 截断但**明确提示用户** | 既不丢库也不静默 ✓ —— 但需要设计定"上限是多少、要不要提示" ✗ |

**我倾向第三种** ✓，但**设计没有规定摘要长度** ✗ ✓ —— 所以列为拍板项 ✓。
**注意**：前端已有 `CHANGE_NOTE_MAX_LENGTH` ✓，所以**前端可能本来就限制了输入长度** ✗ ✓ ——
若前端已限制，则后端 200 截断只是**防御性冗余** ✓，这个拍板项就降为"是否统一两处常量" ✓。
