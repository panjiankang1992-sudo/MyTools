## 第 144 轮：`form` 错值**已定位并修复**（含反向验证）

### 根因

`DraftToBookMapper.formOf(text)` 原文：

```java
if (text.codePointCount(0, text.length()) == 1) {
    return EntryForm.CHARACTER;              // ← 「单个码点 = 单字」
}
```

**它把"汉字单字"与"单字母英文单词"混为一谈** ✗，而且**只看文本、不看学科** ✗ ——
于是英语册里的 **`"I"` 与 `"a"` 被推成 `CHARACTER`** ✗ ✓。

**这与我第 143 轮查到的两件事对上了**：
① `form` 会进公开响应（`CurriculumEntry` 带 `@JsonProperty`）✓ → 用户可见 ✓；
② 生产同册对应条目是 **`word`** ✓ → 迁移后的值是**错的** ✗。

### 修法（最小、且不动汉字行为）

```java
if (trimmed.codePointCount(0, trimmed.length()) == 1) {
    int codePoint = trimmed.codePointAt(0);
    boolean asciiLetter = (codePoint >= 'A' && codePoint <= 'Z')
            || (codePoint >= 'a' && codePoint <= 'z');
    return asciiLetter ? EntryForm.WORD : EntryForm.CHARACTER;
}
```

**单个 ASCII 字母判为 `word`** ✓；**汉字单个码点仍是 `character`** ✓（不受影响 ✓）。

### 测试与反向验证

新增 `singleAsciiLetterIsWordNotCharacter`：**三条一起断言**（`I`→word、`a`→word、`山`→character）——
**必须一起断言**，否则"一刀切改成 word"也能让前两条通过 ✓。

```

反向验证（撤回 asciiLetter 判断，恒返回 CHARACTER）：
  [ERROR] Tests run: 12, Failures: 1
  [ERROR]   DraftToBookMapperTest.singleAsciiLetterIsWordNotCharacter:99 [英文单词 I]
恢复后 cmp 校验：逐字节一致 ✓
全量：Tests run: 409, Failures: 0, Errors: 0, BUILD SUCCESS   （408 → +1）
```

## 第 145 轮：`order` 偏移**是有意为之，不是缺陷**——但暴露出两套约定并存

### 代码里写明了理由

`CurriculumFileImporter` 保留条目字段时**刻意排除 `order`**，并留了注释：

```java
// 不含 `order`：顺序由草稿数组的位置表达，映射时按下标重新编号，
// 再单独保存一份反而会出现"两个顺序"互相矛盾。
```

而 `DraftToBookMapper` 用 **`index + 1`** 赋 `order`（数组位置 + 1）。

**所以"0 基 → 1 基"是刻意选择** ✓，理由站得住 ✓：
**顺序只有一个真相来源（数组位置）** ✓，再存一份会出现两个互相矛盾的顺序 ✓。

**与 `reviewStatus` 一样，它不是缺陷** ✗ ✓ —— 我**不把它记为缺陷** ✓。

### 但确实存在一个**真问题**：两套约定并存

| 来源 | `order` 基 |
| --- | --- |
| **生产内容包**（只读实测 `cn-ty-3-1-pep-2024` v1.0.0）| **0 基**（`0, 1, 2…`）✓ |
| **`DraftToBookMapper`**（管理端发布路径）| **1 基**（`index + 1`）✗ |

**于是**：同一册教材，**迁移进来再发布**之后，条目 `order` 会整体 +1 ✗ ——
相对顺序不变 ✓，但**绝对值与生产内容包的约定不一致** ✓。

### 我**没有**改它，原因

改法只需一个字符（`index + 1` → `index`）✓，**但那是决定"哪个基数是本项目的约定"** ✗ ——
- 若约定是 **0 基**（生产内容包如此 ✓）→ 应改成 `index` ✓；
- 若约定是 **1 基**（映射器如此 ✓）→ 那**生产内容包反而是错的** ✗，要动的是导入侧 ✓；
- **两者我都没有依据判定** ✗ ✓ —— 而且**任选一个都会让另一侧变成"不一致"** ✗。

**这正是我一路在拒绝的那类单方面决定** ✓（与 D1 的 `catalogVersion` 语义差同类 ✗）。
所以我**只把它记录清楚：这是一个需要拍板的约定问题，不是我能单方面改的实现缺陷** ✗ ✓。

### 唯一**未受影响**的一点

无论取哪个基数，**条目之间的相对顺序都不变** ✓ ——
所以**用户看到的排序是一样的** ✓；差别只在"客户端是否展示 `order` 的绝对值"✗（本环境无法判定 ✗）。

### "系统性映射差异"这一项的最终状态

| 字段 | 判定 |
| --- | --- |
| **`form`** `word → character` | ✅ **确认是缺陷，已修复并反向验证**（第 144 轮）|
| `order` 0 → 1 基 | ✅ **确认是刻意设计，不是缺陷**（本文件本轮）；**但暴露出"生产 0 基 vs 映射器 1 基"的约定不一致** ✗ —— **需拍板，我不单方面改** ✗ |

| `meaning`/`pinyinDisplay` `null → ""` | ⚠️ **未处理** —— 用户可见 ✓；用 `== null` 判空的客户端会失效 ✗。**未查清是刻意还是疏漏** ✗ |

## 第 146 轮：`null → ""` —— **来源已定位：导入器统一用 `asText("")`**

### 来源

`CurriculumFileImporter` 写草稿条目/单元/课文时**统一使用 `asText("")`**，例如：

```java
node.put("title", unit.path("title").asText(""));          // 单元
node.put("order", unit.path("order").asInt(0));            // 单元
node.put("title", lesson.path("title").asText(""));        // 课文
node.put("unitId", entry.path("unitId").asText(""));       // 条目
```

**所以"缺失"在导入时被统一表示成空串** ✗ ——
这解释了往返实测里的 `meaning`（语文）与 `pinyinDisplay`（英语）`null → ""` ✓。

### 判定：**风格一致的刻意选择，但确实用户可见**

| 维度 | 判定 |
| --- | --- |
| 是不是刻意 ✗ | **很可能是** ✓ —— 同一个文件里**每个字段**都这么写 ✓，是**统一的空值表示** ✓，不是某一条写漏 ✓ |
| 用户可见吗 ✗ | **是** ✓ —— `meaning`/`pinyinDisplay` 都在 `CurriculumEntry` 的 `@JsonProperty` 列表里 ✓ |
| 影响多大 ✗ | **低** ✓ —— `null` 与 `""` 对绝大多数消费方含义相同（"没有值"）✓；只有**用 `== null` 判空**的客户端会失效 ✗ |
| 是不是缺陷 ✗ | **不判定为缺陷** ✗ ✓ —— 与 `order`、`reviewStatus` 同类：**有一个可辩护的统一约定** ✓ |

### 我**没有**改它，原因

- 改法要动**导入器的多处 `asText("")`** ✗（不是一处 ✗），并且要**先定"缺失该表示成 null 还是空串"** ✗ ——
  又是**一个需要拍板的约定问题** ✗ ✓（与 `order` 的基数、D1 的 `catalogVersion` 语义同类）；
- 而且**风险不对称** ✗：把 `""` 改回 `null` 可能让**依赖空串的现有代码/测试**出问题 ✗，
  而收益只是"与内容包的 `null` 表示一致" ✗ —— **投入产出比不足** ✗；
- 我的余量已经很紧 ✗，**不该在没拍板前动它** ✓。
