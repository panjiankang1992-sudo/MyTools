# 下载全流程耗时分析（2026-11-04）

结论：历史瓶颈主要是排队、同步标签处理和占用执行槽位的状态对账；本批文件的网络传输及存储发布较快。GPU 运行异常已经恢复，但下载与后处理耦合、轮询占槽、整批等待等结构性问题仍在。本轮没有调整并发，也没有实施标签异步化。

分析窗口为北京时间 2026-10-28 至采集时刻。样本包含 143 条下载请求、382 个 download 前缀任务、2205 条步骤记录，另检查了 109 个附件包装任务和 109 个附件对账任务。请求中包含本次排障的重跑与取消记录，不能直接用其终态数量计算业务失败率。109 条附件请求均确认来自 Telegram；APP 的 X 下载另行统计，没有把 QQ、Telegram、APP 混为同一渠道。

**真实等待时间。** Telegram 的 109 个附件合计约 21.5 MB，单个文件中位数约 119 KB。从入站消息 received_at 到下载任务最终成功，中位数 43.6 分钟，最长约 69.9 分钟。从 Download 请求创建到成功，中位数 27.4 分钟，P95 51.6 分钟。后者不包含入口包装任务产生下载请求之前的等待。

**标签放大了所有后续排队。** 当前文件任务顺序执行：下载、存储发布、资产登记、媒体登记、结果回写、缩略图、标签、标签回写，最后才释放下载任务槽位。缩略图和标签虽然配置为 IGNORE，仍然会等待执行、超时或重试结束，并非异步后台任务。

11 月 4 日已确认 CPU 运行异常期间，标签阶段中位数为 86.87 秒；GPU 恢复后的 52 条成功标签步骤记录，中位数为 4.78 秒，P95 仍有 46.85 秒。不同批次的中位数相差约 18 倍，这是观测对比，不是同一文件的控制变量基准测试。阶段间隔还包含 GPU 锁等待、进程启动和上报开销，不能等同于纯模型推理时间。

GPU 协议对模型调用使用单锁，获取锁最多等待 120 秒；近 7 天有 65 条 GPU_BUSY 失败尝试。多条下载同时进入标签步骤时，下载槽位被等待 GPU 的任务占用，网络和存储空闲也无法及时接受下一个附件。历史 128 条成功标签步骤的估算中位数更高，约 137 秒；该历史阶段没有逐条 GPU 驻留证据，不能一概判定全部在 CPU 运行。

**另有 8 个槽位在做轮询。** 线上主 Executor 总并发为 12，附件下载最大并发 4；message_reconcile_attachment_download 最大并发 8，与包装任务共用最大并发为 8 的消息集群。对账脚本每 10 秒查询一次状态，执行期间持续占有调度槽位。

2026-11-03 02:10、02:30 的 execution 起止区间重建结果均为：8 个附件对账任务加 4 个附件下载任务，合计占满 12 个槽位。对账任务运行时长中位数 340.5 秒，本身不传输文件。它们也占满消息集群，使后续附件包装任务不能及时创建 Download 请求，产生入口、下载、对账多层排队。这个问题不由取消排队超时解决。

**X 下载还有批次和队头阻塞。** 线上 download_message_url_batch 的全局最大并发为 1，download_x_user 为 1，download_x_post 为 2；编排集群上限为 4。用户任务每 20 条帖子创建一批，再同步等待该批全部帖子完成。帖子任务又同步等待所有媒体文件的完整处理链路，因而 GPU 标签延迟会逐级阻塞帖子、用户、消息批次。

近 7 天 X 帖子任务排队中位数约 6.5 分钟，P95 约 30.6 分钟；这些是包含事故积压和恢复过程的历史值，不代表当前空闲队列。APP 消息 URL 批次的排队中位数约 100 秒。已经修复的 /media 专用页面读取，成功样本从用户任务开始到首次创建帖子子任务约 2.4～2.8 秒；这不是整个用户下载的完成耗时。X URL 解析步骤中位数约 2.07 秒，整体媒体解析不是本批最主要的持续瓶颈。

**可观测性有明确缺口。** 全部 2205 条步骤记录的 started_at 与 finished_at 相同。代码在终态上报时同时填入同一个 now，不能直接用字段差值声称某步骤耗时为零。上表阶段值按同一次 execution 内相邻终态上报间隔估算，第一步从 execution.started_at 算起；包含启动、重试等待和上报开销，资源故障期间的延迟上报尤其会影响估算。父任务步骤还包含等待子任务，不能再与子步骤相加计算墙钟耗时。Executor 已计算进程 duration，但当前上报链路没有将其用于这两个字段。

另一个统计陷阱是跨服务时钟：143 条 Download 请求与 Scheduler 创建记录的存储时间差中位数为 28800.011 秒。已按 Download 时间加 8 小时统一为北京时间后比较；未处理这个偏移会把任务归到错误日期，或得出负耗时。

缩略图有 124 次失败尝试，均涉及 ffmpeg 调用；这是尝试数量，不是文件数量，也不表示全部文件没有缩略图。目前尚未进一步定位这些 ffmpeg 失败的共同底层原因。标签读取缩略图失败时存在原图/转换兜底，不能用成功缩略图步骤的 0.1 秒代表所有文件处理成本。

**APP 和状态链路核验。** 当前 APP 历史列表逐条查询最多 30 条请求，在一个共享 RLock 内对账并构造结果，健康状态下本次实测约 0.66 秒；不能仅凭这一次读请求认定存在列表性能故障。但外部服务缓慢时，串行状态查询与共享锁可能放大接口时延，宜改为批量只读状态和后台对账。当前对账以请求读取驱动，后台已成功但记录未及时刷新的情况会进一步延长“看起来还没完成”的时间。

本轮核对发现并纠正了此前发布回归：身份补丁覆盖了原 PYTHONPATH，使完整 APP 路由模块遗漏。已基于实际原 APP 发布包创建 app-download-identity-20261104-v2，保留原加载路径及身份修复，恢复列表和详情接口。两条已恢复请求原 APP 条目仍绑定旧失败请求的问题，也已通过同所有者、同参数、成功终态验证后修正绑定。原失败任务没有被改成成功。APP 本地 SQLite 有完整备份、参数化 CAS 更新和幂等恢复审计；二次执行变更数为 0。实际列表及详情均验证为 SUCCEEDED，文件数分别为 26 和 76。

没有建立所有 Telegram 回执的入站、业务完成、发送提交、渠道确认的统一关联时间线，因此本报告不给出独立“回执发送耗时”百分位。附件对账每 10 秒轮询及其排队，可能使业务状态更新晚于下载完成；这与渠道本身发送缓慢不是同一结论。

建议按以下顺序实施优化：

1. 将“文件下载归档成功”与“标签/缩略图补全”拆为独立状态和任务。网络下载完成并登记后释放下载槽位；GPU 后处理使用独立队列和并发控制。界面分别展示下载完成和后处理状态，保留审计、失败重试、所有权及回滚能力。
2. 把附件对账移出通用 Executor 的长时间占槽任务，改为服务内有界批量对账或终态事件驱动。对账不能继续消耗 12 个业务槽位中的 8 个。
3. 对大用户下载和小 URL 请求做公平调度及限量投递，避免一个用户批次阻塞全局单槽；减少父脚本长时间同步等待。保留 X 端限流及 GPU 单模型互斥，不能简单扩大所有并发。
4. 加 GPU 实际驻留检查、CPU 回退保护及资源水位约束。已完成的启动设备检查只能降低风险，不能代替 size_vram 和实际推理后端验证。对已被 Scheduler 明确裁定失效的报告，设计可审计的隔离恢复，避免单条旧租约永久阻塞整个节点。
5. 补齐真实步骤 startedAt、finishedAt、duration，以及 queuedAt、fileReadyAt、tagsReadyAt、notificationAt。统一时间口径，建立渠道、请求、父子任务的关联观测；再用同一组小图、大图、视频和批量样本验证收益。

优先验收下载可用时间、网络槽位利用、GPU 队列等待和回执及时性，不以“总并发调大了”作为完成依据。本批样本主要是小文件，不能据此推断大视频的传输耗时，也不承诺尚未实施的异步改造能达到某个固定倍率。
