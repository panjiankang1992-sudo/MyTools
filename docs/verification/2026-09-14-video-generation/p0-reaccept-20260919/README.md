# 首帧模式补边修复后的重新验收（2026-09-19 维护窗口）

## 为什么要重验

首帧模式的补边在**控制输入**里是中性灰（`PAD_COLOR_HEX = 0x808080`），但模型会把成片里这两条边改成
任意颜色：同一张 Krea 生成图，一次偏蓝（26,109,186）、一次偏黄，而 P0 那张白底产品图恰好灰。
也就是说 **首帧模式的验收结论依赖素材**，此前没暴露。

修复（`video_generate/1.0.0 → 1.0.1`）：出片与封面阶段按**控制帧量出的几何**把补边覆盖回中性灰，
几何来自工作流实际收到的帧，不重新推导 ffmpeg 取整；结果里新增 `padRects` 供复核。
同时把验收判据从"边缘不白"升级为"**补边必须是中性灰**"（亮度在 0.502±0.06 且三通道离散度 ≤ 12/255）——
旧判据只测亮度，蓝边 0.36、黄边约 0.6 都能骗过去。

## 窗口设置

- 环境：生产链路（视频服务内部接口 → 调度器 → 执行器 → `video_generate/1.0.1`），非旁路跑法。
- 窗口动作：暂停含 GPU 步骤的任务定义并排空在途任务；网关路由在窗口内关闭；结束恢复原状。
- 素材：**3 个不同主体**（冷白底产品图、暖色生成图、真实风景照）× **2 个固定种子**（42、932）。
- 参数：单图首帧、832×480、49 帧、16fps，固定提示词（比的是补边与构图，不引入提示词变量）。
- 判据（客观部分）：任务成功、补边中性灰、画面确实在动、几何为 832×480/49 帧。

## 这次部署顺带修掉的生产问题

补边修复本身很小，但把它发上去暴露了一串只在"同一服务线的第二次发布"才会出现的问题，
都已修并提交（见 `fix(deploy)` 那条提交）：

1. **结果 schema 没同步注册**：执行器上报结果时调度器按 `task_definition.result_schema` 校验，
   包新增 `padRects` 而注册值还是旧的 → 推理跑满 8 分钟后才以 `TASK_RESULT_SCHEMA_INVALID` 失败。
   已加 V158 同步注册，并把"包 schema == 注册 schema"做成 activate 阶段的硬预检（放在调度器健康之后，
   因为 `systemctl restart` 对 Type=simple 立即返回，Flyway 可能还没跑完）。
2. **执行器 journal 的人工诊断门禁把节点拖成 OFFLINE**：那条被拒的上报变成 `DIAGNOSTIC`，
   执行器据此拒绝领取任务**并且心跳失败**；旧任务终态后该记录已无意义，按诊断结果清掉后节点恢复。
3. **发布脚本只支持首次发布**：env 已存在就拒绝、每次重新生成共享令牌、基线里已含同版本包导致
   `copytree` 撞车、`current_executor_jar()` 在 drop-in 指向半成品发布时直接失败——
   都已修成可重复发布（同版本必须同内容、令牌沿用上一版、jar 有兜底）。
4. **配置依赖**：主机 python 升到 3.14 后丢了 `pymysql`，已装回（`python3-pymysql`）。

另外发现一处与本次无关的遗留问题：`media_submit_analysis:1.0.0` 包里的 `result.schema.json`
不是合法 JSON（媒体服务线的包）。本次预检已收窄到"本发布负责的包"，不让视频发布为它背锅，
但该包自身仍值得媒体侧修一次。
