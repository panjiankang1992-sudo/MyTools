## 6. 测试目标约束（已核对并加固）

方案与验收要求 E2E 显式指向本地或独立测试环境。已核对并处理：

- `scripts/verify-release.mjs` 用 `spawnSync` 且**未传 `env`**，因此子进程**继承** `E2E_TARGET`，调用链是通的；
- 但真正的风险是**不设 `E2E_TARGET` 时默认打到公网**，那会污染线上统计。已在 `verify-release.mjs` 中加守卫：
  - 未设置 `E2E_TARGET` → 记为 `not-executed` 并说明原因，**不跑**；
  - `E2E_TARGET` 指向 `yuyutian.top` → 同样记为 `not-executed`，**本地验收不得打到生产**；
  - 其它目标（本地或独立测试站）→ 正常执行。

三种情形都实测过：

| 场景 | 命令 | 实际结果 |
| --- | --- | --- |
| 未设置目标 | `npm run verify:release` | `SKIP end-to-end — 未设置 E2E_TARGET…`，汇总「5/6 通过，1 项未执行（不计为通过）」 |
| 目标指向公网 | `E2E_TARGET=https://toolbox.yuyutian.top npm run verify:release` | `SKIP end-to-end — E2E_TARGET 指向公网站点…` |
| 目标指向本地（死端口） | `E2E_TARGET=http://127.0.0.1:23999 npm run verify:release` | **真的执行了**（147 s）并按预期 `WARN`，证明目标确实被使用、守卫没有误伤本地运行 |

第三种情形是有意设计的反证：既证明守卫不会拦住合法的本地运行，也证明 `E2E_TARGET` 真的被下游消费而不是被忽略。

**结论**：从此 `verify:release` 不能再代表线上验收，也不会在未指定目标时偷偷打到生产。后续所有 E2E 都必须在设置了本地或独立测试站 `E2E_TARGET` 的前提下运行。

### 6.5.1 用例抓出的两个真实缺陷

写测试时暴露了实现里的两个逻辑错误，都已修正（不是改测试）：

1. **操作身份判定错误**。原先用「产物是否过期」反推「内容是否变化」，但纯版式变化同样会让产物过期，于是改一次格距再生成就会**凭空产生一个新的操作身份**（统计上会多记一次使用）。改为显式记录上次成功生成时的内容修订（`generatedContent = {input, processing}`），只有原文或处理参数变化才算内容变化。

### 6.12.7 更正：解码失败是我的测试夹具问题

上一轮我把 `WORKSHEET_IMAGE_DECODE_FAILED` 记为「产品缺陷、原因未查明」。查清了，**是我的夹具注入方式有问题**：

### 6.22.2 W15 已通过：真实取消取证 + 修掉一个契约级缺陷

上一轮我判断「真实取消无法复现，因为识别太快」。本轮按自己写下的解除条件做了两件事：

**① 造出足够慢的识别**：新建 `samples/ocr-fixture-big.png`（3000×1160、18 行文字），真实识别耗时约 **2020 ms**，取消窗口稳定。

**② 一测就暴露出真实缺陷**。第一次取消的结果是：

```
取消后立刻: 状态「已取消本次识别，原文与图片都保留。」队列「识别中」
等待 3 秒:  队列「已完成」并带识别文本   ← 结果仍然落地了
```

**取消只改了文案，后台照跑并把结果落地**——这正是契约 §4.1 第 5 条明令禁止的行为（「不能仅让取消按钮改变文案而后台继续覆盖」「不通过隐藏 loading 冒充已取消 worker」）。

**根因**：`currentJobId` 这个变量**声明了、在取消函数里用了，却从未被赋值**。于是 `service.cancel()` 收到的永远是 `null`，取消根本没有传到引擎。

**修复**：识别每一项前 `currentJobId = item.id`，`finally` 中复位；被取消的任务回到「待识别」而不是留下半份结果；取消时立即把运行项标记为「已取消」，界面不再显示「识别中」。

**修复后实测**：

```
取消后立刻: 队列「待识别 · 已取消」，状态「已取消本次识别，原文与图片都保留。」
等待 6 秒（约 3 倍识别时长）: **没有产出任何候选**，原文仍为「取消前的原文」
取消后仍可继续识别
```

这个缺陷只有**用足够慢的识别去测**才会暴露——识别太快时，取消点不到窗口，看代码也容易误以为「有 currentJobId 判断就是接上了」。

**W15 已记为 `pass`。**

## 6.38 发现并修掉缺陷 13：多页字帖只能看到第一页（本轮）

核对 v2 预览时发现：`WorksheetPreview` 接受 `page` 与 `zoom` 两个 prop，但**整个页面没有任何控件去改它们**——旧页面有 `.page-controls`，v2 没有。

`page` 只在生成时被设为 1，因此**多页字帖永远只能看到第一页**，用户无法在打印前检查第 2 页及以后。这是用户可见的功能缺失（契约与 W38/W39 都涉及多页预览）。

### 6.38.1 修复

在 `WorksheetV2View` 的输出区加入：

- **上一页 / 下一页**（`v-if="artifact.pageCount > 1"`）+ 「第 N / M 页」指示；
- **适应窗口 / 实际大小** 切换（`zoom`）。

两者都接在既有 ref 上，没有新增状态。

### 6.38.2 实测（真实浏览器）

难点是**造出真正的多页产物**：整册教材导入会触发 200 项上限，而数量下拉在视口之外。解决方式是**先 `scrollIntoView` 再派发真实鼠标事件**（Naive UI 的下拉不响应合成事件）：

```
数量框(滚动后): {"x":374,"y":684}
选项:           {"found":true}
产物:           {"tag":["2 页"],"alerts":[]}
翻页:           {"hasControls":true,"indicator":"第 2 / 2 页"}
```

即：200 项 → 2 页产物 → **翻页控件出现 → 点「下一页」后显示「第 2 / 2 页」**。

### 6.38.3 尚未补的端到端断言

本条**尚无端到端断言**保护：复现它需要在测试里做「滚动到数量控件 → 真实鼠标事件选随机抽取 → 生成 2 页」。本轮预算已用尽，已如实记录，**不把它写成已有回归保护**。

## 6.39 系统核对待实现的 props/emits，又找到缺陷 14（本轮）

按上一轮的想法做了一次**系统性核对**：逐个检查子组件声明的 emits 是否都有处理者。方法很简单，却立刻命中一处。

### 6.39.1 缺陷 14：「选择词条」按钮点了没反应

`WorksheetPreview` 声明并触发了 `select` 事件（空态里的「选择词条」按钮），但 v2 视图只接了 `@retry`：

```
空态按钮: {"exists":true,"text":"选择词条"}
点击:     {"ok":true}
点击后:   {"alerts":[],"stillEmpty":true}   ← 完全没有反应
```

旧页面是 `@select="activeTab = 'entries'"`（切到条目 tab）；v2 没有这种 tab，所以**照搬旧写法不成立**。

### 6.39.2 修复要针对 v2 的实际布局

先试了 `goBackToEdit`，实测**没有可见效果**——因为空态出现时用户本来就在第 1 步，回到编辑是空操作：

```
点击前 step: 1 输入内容 (active)
点击后 step: 1 输入内容 (active)   ← 无变化
```

改为 `focusEntries()`：若停留在最后一步先回到编辑，然后**把选词区滚动到视口内**。用 600px 高视口实测：

```
点击前: {"top":631,"scrollY":0}     ← 选词区在视口外
点击后: {"top":328,"scrollY":303}   ← 已滚入视口
```

**按钮从"点了没反应"变成有明确可见效果。**

### 6.39.3 这类问题为什么容易漏

`WorksheetPreview` 的代码本身是**完整**的：有 emit 声明、有按钮、有点击处理。缺的只是**父组件的监听**——而 Vue 对未监听的自定义事件**不报错也不警告**（会退化为原生 DOM 事件），因此构建、类型检查、单元测试全都发现不了。

这与缺陷 13（传了 prop 却无人修改）是同一类：**跨组件的"接线遗漏"，单看任何一侧都正常。**

## 6.49 W39 核心判据：三处使用同一 artifact（本轮）

W39 的核心是「**预览、下载与打印均使用同 revision 的同一 artifact**，下载 SHA-256 与该 artifact 一致」。此前只验证了「下载的是真实 PDF」和「打印窗口有下载入口」，**没有验证两者是不是同一份文件**。

### 6.49.1 做法

1. 点「导出 PDF」按钮，让浏览器**真实落盘**；
2. 独立读文件算 SHA-256；
3. 打开打印预览，取窗口里下载入口的 `blob:` 地址，在页面内 `fetch` 后用 `crypto.subtle` 算 SHA-256；
4. 比对。

### 6.49.2 实测

| 来源 | SHA-256 | 字节 |
| --- | --- | --- |
| 「导出 PDF」按钮落盘的文件 | `1f19fc31f5e0f49f45341dcfa0c6f516be053ab6497d0845b9a9037d10170880` | 61669 |
| 打印预览窗口下载入口的 blob | `1f19fc31f5e0f49f45341dcfa0c6f516be053ab6497d0845b9a9037d10170880` | 61669 |

**两者 hash 完全一致** → 预览、下载与打印确实是同一份 artifact，**不是各自重新生成**。

## 6.81 尝试用模拟替代实机验证软键盘遮挡：**结论是不可替代**（本轮）

上一轮把 W42 的阻塞收窄到一条：「软键盘是否遮挡当前输入/错误/主要操作」。本轮尝试用 CDP 模拟掉这一条。

### 6.81.1 做法与结果

用 `Emulation.setDeviceMetricsOverride` 把手机视口从 844px 压到 508px（典型软键盘高度），输入框保持焦点，测量其位置：

```
可见高度: 508
输入框:   { top: 459, bottom: 687 }
是否被遮挡: true
是否在可视区内: false
当前焦点: editor-area
```

**表面结论是"输入框被遮挡"。**

### 6.81.2 但这不是产品缺陷——是我的模拟不成立

核对后确认：

| 项 | 事实 |
| --- | --- |
| `setDeviceMetricsOverride` 改变的是**布局视口** | 不是 `visualViewport` |
| 真实软键盘弹出时 | 浏览器会**自动把聚焦元素滚入可视区**（iOS/Android 的既定行为） |
| 我的模拟 | **不会触发**这套浏览器逻辑，因此"没滚入"是模拟的产物 |
| 代码里有没有自研处理 | 只有一处 `scrollIntoView`（步骤切换用），**没有 `visualViewport` 监听**——说明它依赖的正是浏览器默认行为 |

**所以 `被遮挡=true` 是模拟假象，不能作为缺陷上报。**

### 6.81.3 这正是"缺陷 19"的同类陷阱

| 事故 | 我的错误 | 结果 |
| --- | --- | --- |
| 缺陷 19 | 读了后端不使用的字段 | 报了一个不存在的缺陷 |
| 本轮 | 用不触发浏览器逻辑的模拟去测依赖浏览器行为的场景 | **在报告前发现，未上报** |

**这次是在把结论写进报告之前发现的。**

### 6.81.4 结论：这一条确实需要实机

- **没有**可用的模拟手段能替代真实软键盘；
- 该判据依赖浏览器默认行为，**实机验证成本很低**（打开页面、点输入框、看是否可见）；
- **W42 保持 `blocked`**，阻塞点仍为这一条。

**把这个实验记录下来，是为了避免以后有人（包括我）再走一遍并误报缺陷。**

## 6.84 W13 中文 CER 未达标：把"精度不够"变成**可验证的假设**（本轮）

W13 是唯一的功能性失败项，此前只记录了结果（CER 15%）。本轮分析**错在哪、为什么错**，把阻塞从"精度不够"推进到"一个可检验的假设 + 实验设计"。

### 6.84.1 错误模式指向"语种误判"，而非"认字不准"

`ocr-fixtures.json` 记录的错法：

| 真值 | 识别结果 | 性质 |
| --- | --- | --- |
| 花朵 | **`esx`** | 汉字区被当成**拉丁字母**输出 |
| 白 | 日 | 形近字混淆（正常的引擎误差） |

**`花朵 → esx` 不是"看错字"，而是"看错语种"**——Tesseract 判定该区域是拉丁文并输出了字母。形近混淆（白/日）属于引擎固有误差，而语种误判属于**配置问题**。

### 6.84.2 假设：中文语言集含 `eng` 导致拉丁化输出

```ts
// src/services/worksheet-ocr.ts:78
return language === 'chinese' ? ['chi_sim', 'eng'] : ['eng'];
```

中文模式加载 `chi_sim + eng`。多语言模型下，引擎可以对汉字区域选择 **Latin 输出路径**，从而产生 `esx` 这类垃圾串。

**这是个一般性配置问题，不是单个夹具的调参问题**——它影响所有纯中文内容。

### 6.84.3 为什么本轮**没有**改

| 理由 | 说明 |
| --- | --- |
| 可能影响混合内容 | 中文工作表里可能出现英文词（如字母/单词），去掉 `eng` 会让这些内容识别不了 |
| 单个夹具不足以判定 | 现有中文夹具只有 1 张（另有 1 张 32px 变体）。**在一张图上调出好成绩，正是契约禁止的"挑样本"** |
| 需要 A/B 而非单向改动 | 必须比较 `chi_sim` vs `chi_sim+eng` 在**多张**中文夹具上的 CER，才能判定 |

### 6.84.4 建议的实验设计（下一轮或由你决定是否做）

1. **扩充中文夹具**：≥5 张，覆盖不同字号（32/44/64px）、不同版面（词表/句子）、不同对比度，**全部清晰**（低对比度属 W14，不混入）；
2. **A/B 两组**：`['chi_sim','eng']`（现状）与 `['chi_sim']`；
3. **指标**：逐图 CER + 平均 CER + 拉丁字符占比（专门衡量语种误判）；
4. **判定**：若 `chi_sim` 组平均 CER 显著更低**且**拉丁字符占比明显下降，则这是**系统性修复**，可提交你决定是否采纳；否则维持现状并明确记录 CER 未达标的原因。

**在此之前，W13a 保持 `fail`。**

原状态：**"中文 OCR 15%，未达标"**——接手的人不知道下一步做什么。

现状态：**"错法是语种误判（花朵→esx）；首要假设是中文语言集含 eng；已给出 A/B 实验设计与判定标准；未擅自改动以免影响混合内容或变成调参"**——可以直接执行。

## 6.87 OCR：字体是一个真实变量，但误差集中在少数几个字（本轮）

上一轮结论是"与字号无关、不可调"。本轮补测**字体**这个变量（此前 8 张全部是 PingFang 系现代 UI 字体；Tesseract 的 `chi_sim` 训练集以印刷体为主），新增 3 张 **宋体（Songti SC）** 夹具，合计 **11 张**。

### 6.87.1 字体确实有影响

| 夹具 | CER |
| --- | --- |
| **宋体 32px** | **5.00%** ← 达标 |
| **宋体 44px** | **5.00%** ← 达标 |
| 宋体 64px | 15.00% |
| PingFang 系 8 张 | 5%—20% |

**宋体在 32/44px 两张上达标**，说明字体与版面对精度有实质影响——**上一轮"与字号无关"的结论过于绝对**。

### 6.87.2 但更关键的发现：误差**高度集中在个别字**

统计 11 张里"`朵` 是否被认出"：

**11 张夹具中，`朵` 全部识别错误**（被认成 采/洒/丰/杀/未/打）。`白` 也多数被认成 `日` 或 `和`，并常多出一个 `人`。

这不是"普遍精度不足"，而是**少数几个字系统性识别失败**：

| 字 | 识别结果 |
| --- | --- |
| 朵 | 采 / 洒 / 丰 / 杀 / 未 / 打（**11/11 失败**） |
| 白 | 日 / 和 |
| （多余） | 人 |

**这解释了为什么平均 CER 下不来**：20 字里错 2—4 个，CER 就是 10%—20%。

### 6.87.3 这一条改变了结论的性质

| 之前的说法 | 现在更准确的说法 |
| --- | --- |
| "引擎在中文上的能力边界" | **"少数几个字系统性识别失败（`朵` 必错）"** |

前者意味着"整体不行、只能接受"，后者意味着**存在具体的、可能改进的点**（如该字的语言包覆盖、或用词表后处理纠正）。

**并且它给了一个低成本的实用改进方向**：既然错误集中在已知的几个字上，可以在**候选校对环节**对这些易错字做提示（而不是改引擎）。

**许可证注意**：`@tesseract.js-data/*` 的 `package.json` 声明 MIT，但其内部 `traineddata` 源自 tessdata 项目（Apache-2.0）。清单按包声明如实记录，并已注明这一差异；正式发布前如需严格合规，应一并保留 tessdata 的许可证声明。

`public/ocr/` 已加入 `.gitignore`（与 `public/pdfjs/` 同样属于生成产物），构建前需运行 `npm run prepare:ocr`。

## 8.2 B7：`npm install` 失败的根因与修复

**根因**：`toolbox-web/node_modules` 不是 npm 管理的目录，而是 `prepare:local` 用符号链接铺出来的复用层（框架包指向 `webapp/node_modules`，四个 PDF 库指向 `.runtime-deps`）。`echarts` 在 `package.json` 里声明为依赖，npm 在 `toolbox-web` 内执行安装时会对这个链接做 reify，并运行它的 `prepare` 生命周期脚本 `npm run build:lib && husky install`；链接目标 `webapp/node_modules/.pnpm/echarts@6.0.0/.../echarts` 没有 `build/build.js`，于是必然失败并报 `MODULE_NOT_FOUND`。`--ignore-scripts` 与 `npm_config_ignore_scripts=true` 都没有阻止该脚本执行。

**修复**：让 `toolbox-web` 成为真正的独立 npm 工程——依赖全部从 registry 安装到自己的 `node_modules`，不再与 `webapp` 共享目录，也不再创建任何符号链接。原 `scripts/prepare-local.mjs`（链接逻辑）删除，替换为只做校验的 `scripts/verify-local-deps.mjs`；`prepare:local` 保留为同名脚本但行为改为校验，另加语义明确的 `verify:deps`。README 对应段落同步改写。

设计文档 `2026-10-02-public-toolbox/implementation-handoff.md` 原本就把 `prepare:local` 定位为「精确版本暂时装不了时的本机开发退路」，并要求「发布前仍须补干净环境安装验证」。这次的干净安装验证正是此前缺失的一步，结论是 registry 安装可用，退路不再需要。

**验证（真实结果）**：

| --- | --- |
| 从零安装 | 把原符号链接目录改名后 `npm install` → `added 229 packages in 2m`，`postinstall` 的 PDF 资产准备成功，退出码 0 |
| 依赖来源 | `vue`/`naive-ui`/`echarts`/`pdf-lib`/`tesseract.js`/`pinyin-pro` 均为真实目录（非符号链接），版本与声明一致 |
