# QQ 下载失败恢复验证（2026-09-21）

## 根因与修复范围

1. 最近五条 QQ 的 X 链接在创建调度任务时失败。消息入口将 HTTP 下载切换为 X 编排后仍携带 `itemId`、`fileName`；编排参数 schema 拒绝这两个字段，下载入口把调度器 422 包装为 503，自动化提交十次后失败。下载服务现在仅在三个编排类型中剔除这两个已知字段，持久化原始请求仍保持不变，普通 HTTP 下载继续保留字段。
2. 四类启用的下载任务并发上限遗留为零。HTTP 子任务没有任何派发记录，最终排队超时；服务健康、执行器在线均不能证明可下载。`V161` 恢复 HTTP 容量 8，其余三类容量 4，并新增只读容量检查，不调整视频任务容量。
3. 首次标签生成后，标签模型驻留显存；原 GPU 协调逻辑仍要求完整冷启动所需的 10 GiB 空闲容量，后续标签出现 `GPU_MEMORY_UNAVAILABLE`。不可变标签包 `1.4.1` 只允许复用相同模型已分配的显存，仍拒绝其他模型、无效显存报告及重复驻留记录，并保留至少 1 GiB 运行余量。`V162` 只切换四类下载和独立标签任务，视频分析保持 `1.4.0`。

## 发布与恢复边界

- 仅使用当前 SSH 通道。未切换全局 `releases/current`，未覆盖旧包或旧 JAR，未改动其他任务中的视频开发文件。
- Scheduler 数据变更使用 Flyway；补跑使用正常下载 API、调度 API。没有直接脚本修改 Scheduler 表。
- 发布核验发现 systemd 覆盖顺序、非 root 目录权限和历史同名任务版本唯一约束问题。最终迁移按版本倒序递增；失败的 `V162` 记录经标准 Flyway `repair` 后重新应用，`V161`、`V162` 均成功。
- 下载服务使用 `qq-download-contract-20260921-v1` Python 覆盖目录；执行器使用 `qq-tag-reuse-20260921-v3` 中的完整、带校验索引的包集合；Scheduler 使用 `qq-tag-reuse-20260921-v4` JAR。其他代码和配置以原在线版本为基础保留。
- 恢复范围仅限本次确认的五条原消息。第一条探测因零容量超时后使用独立幂等恢复请求，其原失败记录保留；其他四条沿用原始幂等请求。不批量重试历史过期附件。
- 生产审计位于 `runtime/repairs/qq-download-contract-20260921/`，仅服务端保存原记录、校验结果及稳定回执幂等键。仓库不保存消息正文、来源 URL、凭据或实际媒体内容。
