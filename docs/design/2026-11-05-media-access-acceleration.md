# 家庭媒体访问加速设计与实施计划

### 2026-11-09 实施与模拟器验收补充

公网中继现已在保留登录会话的鸿蒙模拟器中完成真实媒体验收。修复了 WebSocket 握手对重复普通响应头的误拒绝：普通头验证名称后直接忽略，五项握手关键头仍禁止重复，证书链、域名、Accept、扩展和子协议检查保持严格。启动及非阅读页面不再全量拉取书源；进入阅读时补拉，离开阅读时只取消书源 GET，原有待写队列、已发写请求及轻量书架、进度同步继续保留。

净版显示“公网中继”时，图库、三次连续图片切换、返回当前图片定位均通过；真实视频经票据测速选择 CHANNEL，起播后拖动到约 35 分钟仍继续播放。验收保留了原有图片缓存，界面观测的准备时间不能当作同条件提速倍数。重启恢复登录及工具首屏通过。当前网络的真实 IPv6、LAN 路线没有新增通过记录。

固定 512 KiB 的诊断出现过完整通道 2.063 秒和原生 HTTPS 总计 3.004 秒（正文 1.315 秒），也出现过部分接收和超时，说明本轮网络波动显著。慢候选仍被质量门槛拒绝，不据单次成功承诺固定速度。没有收益证据的 PING/PULSE、启动 HTTPS 基线和原生句柄诊断已从交付版移除；两次未覆盖探针流量的服务器采样也未被用来排除拥塞。

完整结果、部署校验及签名包见 `output/app-channel-20261109/verification.json`。服务端净版已经 Python 3.12 回归后部署，客户端签名包已安装到模拟器；本轮没有操作真机，也没有修改客户端系统 DNS、代理、路由或安装系统 VPN。

交付分批进行。第一批覆盖 App 的媒体读取、缓存和服务端图片预生成，复用已经上线的家庭网关、原片分段接口及登录会话。第二批在同片验证收益后接入适合手机网络的播放副本。云端中转与 CDN 的采购取决于两条现有线路的实测，以及需要支持的并发人数。

## 1. 选择线路

家庭 LAN 通过身份验证后始终优先。外网只在当前已验证的 IPv6 入口和当前账户的公网入口之间选择。关闭应用内通道时，小接口沿用现有路由。对媒体库预览 GET，分别记录响应首块时间和完整传输时间，估算相同字节数在两条线路上的完成时间。先使用 IPv6，通过少量真实请求采样另一条线路，每次只下载一份。估算值做平滑，样本过期、网络改变或账户切换后重新学习。只有差异超过阈值才改变首选。

超时、断流可以对可信备用入口重试一次。退出页面、取消、解码错误和权限错误不作线路故障处理。视频使用同一网络的近期样本做起播选择，保留原有票据、位置和暂停状态。播放器准备事件用于记录首播耗时，与下载速度分开。局域网和外网分别设定兜底期限。

### 应用内通道选路增量（2026-11-06）

启用应用内通道后的优先级为：已认证 LAN → 已验证 IPv6 的 WSS 直连候选 → 当前账号精确可信公网 HTTPS 来源的 WSS 中继候选 → 原公网 HTTPS 业务接口。公网候选要求 `origin === serviceOrigin`，不依赖 IPv6 发现成功；它不扩大 JWT 可发送的主机范围。TLS 系统证书链和叶证书 SAN 主机名验证通过后才发送认证头，不允许以跳转、更换域名或关闭证书验证建立中继。

候选必须先完成 pinned `ProfileApi` 正常身份验证，再从本进程随机能力入口流式读取固定 `/api/app/v1/connectivity/transport-probe`。服务仅在已认证 WSS 内返回 HTTP 200、`Content-Length: 524288`、`Cache-Control: no-store` 和 `byte[i] = i % 256` 的 512 KiB 正文。客户端在 2,500 毫秒总探针预算内验证每个字节和完整长度，禁用代理和缓存，不保存正文；部分数据、首字节和握手成功均不算通过。直连候选总预算五秒，公网候选十秒，一轮通道选择十五秒；该候选预算包含握手、身份和质量，服务发现沿用独立截止时间。公网冷 TLS 连接可使用较长握手预算，质量门槛保持 2.5 秒。

只在当前账号、线路代次和原能力入口均未改变时同步提交通道。直连成功的头像徽标为“应用内通道”，中继成功为“公网中继”。未确认候选失败只关闭候选，不广播全局通道故障；全部失败后使用原公网业务入口。同一网络内记录失败直连，并保持已验证的中继，不因定时发现而反复切回直连。真实网络变化和用户重新检测时清除记录；LAN 仍保持最高优先级。旧请求及旧异步结果不能覆盖新线路或新账号，写操作不自动重放。

公网中继复用当前 Cloudflare Tunnel：仅对已有可信公网主机的 `^/_mytools/app-channel/v1$` 精确路径增加到 `http://127.0.0.1:23483` 的规则，位于该主机既有业务规则之前，其他规则保持相对顺序。家庭端服务仍只监听回环；普通业务逐笔沿用原鉴权。登录、刷新、安全存储及既有会话期限不变，不安装系统 VPN，不修改系统 DNS、代理或路由。

通道连接与质量判断异步执行，工具仍为应用首屏。书源全量列表的 `GET`/`HEAD /api/app/v1/reader/sources` 与媒体共享四个批量位置，五条 WSS 中保留一个控制位置；取消释放所属请求，排队超时返回完整 503，局部容量不足不拆健康通道。媒体仍保留独立的真实票据 Range 验证及单视频回退。

上述内容记录选路与质量准入实现，不代表公网中继的真实业务已通过验收或取得速度提升。需要在实际网络确认徽标、完整大书源列表、图片加载和视频起播/拖动，并结合服务端完成字节及失败计数判断。此前真机记录按各自测试日期保留，不能外推为本轮中继结果。

## 2. 图片优先级和磁盘缓存

目录保留前方三至六屏，详情保留前后十二项。远近决定排队顺序，窗口大小与同时下载数量分开控制。下载共享两个位置，后台预取最多使用一个，当前图、屏内卡片及高清升级可以使用预留位置。缓存命中、合并同图请求发生在占用位置之前。进入视频准备阶段暂停新的后台图像下载，离开时恢复。切换查询和退出时解除排队，避免旧异步结果更新新页面。

缩略图与详情预览分别按容量和数量裁剪。兼容已有缩略图并复用已有高清文件。清理与统计覆盖两个目录，保护在用图片和正在写入的临时文件。

## 3. 服务端生成

对已经提交入库的 READY 图片生成 512 和 2048 两个版本。后台最多使用一个解码位置，给前台实时请求留容量。内容摘要、媒体 ID、所有者和尺寸共同标识版本。生成复用现有鉴权、尺寸上限、临时文件和原子发布逻辑。最近图片回补分批，优先最新记录，设置存储水位和单批数量。后台失败不会改变原媒体状态，原有按需生成可恢复。

## 4. 视频交付

用已有下载来源短片和大 MP4 分别验证 Range、起播及拖动。先比较同片同区间的两条线路，区分传输耗时与索引开销。第二批针对大视频验证离线播放副本。尾部索引可用 faststart 无损重封装；持续吞吐低于原片码率时需要低码率版本。HLS 的清单和每段都需验证用户票据、媒体状态，需覆盖过期续签和鸿蒙播放器定位。只在可用版本生成完毕后向客户端提供。按真实设备数据决定启用范围和码率。

## 5. 验收及回退

1. 记录当前签名包、媒体服务基线和可用真机的旧版表现。
2. 用可控网络样本验证线路选择、网络切换、失败重试及取消。对磁盘命中、并发优先级、缓存上限和跨账户内容分别验证。
3. 媒体服务独立 Maven 测试并打包。仅增量发布所需类，发布前校验运行基线，启动检查失败回退旧包。
4. 构建签名 HAP、覆盖安装。相同图库检查列表到可见图片、点击到详情、连续滑动和返回。区分冷/热缓存。用第 30 项验收下载来源视频。
5. 记录测试条件和结果。服务端回退到前一运行包，客户端可覆盖安装上一签名包。优先保留原片、原有缓存和登录数据。

### 真机验收顺序

1. 用同一台手机、同一蜂窝网络与相同的媒体清单，在旧版和新版各测一轮，再交替复测。同一内容固定首次访问或已缓存条件，不清除登录数据。分别记录从进入列表到首屏可见卡片全部出图，从滑动到目标图出现和高清完成的时间。各报告中位数和慢样本，样本不足只列原始结果。
2. 用截图中的第 30 项确认下载来源视频起播、暂停拖动和续播，再用大视频分别测点击至第一帧、拖动后至画面恢复，以及连续播放的卡顿时长。记录实际媒体线路，区分应用全局线路和单视频线路。
3. 在受控试点中开启视频副本，首次播放走原片，生成完成后重复打开同一部视频。确认清单、分段、清晰度切换和原片回退。在家庭 Wi-Fi、蜂窝直连和仅公网三种可用条件下分别记录。达到实际收益后再决定是否扩大转换范围。
4. 如同片、同字节在两条外网线路的持续吞吐都低于最低可接受码率，补测家庭上行及另一运营商；确认瓶颈后再评估第三线路或云端存储费用。

基础增量已在 Ubuntu 发布。匿名图库返回 401，未知播放票据返回 404。回补后检查最近 48 张符合条件的图片，读取之前全部已有 512 和 2048 两个尺寸的缓存。抽查同一张图片的两次本机 HTTP 读取，512 像素返回 29,932 字节，2048 像素返回 110,135 字节，重复读取内容一致，耗时 14.8～17.7 毫秒。这是源站测量。

### 更换网络后的真机复测与视频选路修正

同一台手机在新网络上通过 IPv6 服务身份挑战，前台标识显示 IPv6。使用隔离的诊断构建，App 将当前合法视频票据用于直连和本账户公网入口，交替读取同一原片的 1048576～1572863 字节。四次均收到完整的 HTTP 206，并在手机内比较 SHA-256；诊断只记录取样耗时、传输量及校验结果。四次耗时依次为 IPv6 14.698 秒、公网 1.831 秒、公网 1.897 秒、IPv6 12.520 秒。对这段 512 KiB 数据，本轮公网端到端有效速率约为直连的 7.3 倍。IPv6 在首批数据到达时间上仍较短。该诊断代码未打入交付包。

仅依赖图片测速及视频准备事件会错过“已经显示时长，但播放时钟迟迟不动”的情况。新的外网大视频入口在网络验证通过后，按真实票据在 IPv6 与公网各取最多 256 KiB，一次比较最多等待 4.5 秒。用时差超过阈值才改选公网，同一网络与入口组合复用五分钟。家庭 LAN 直接播放。网络、会话或媒体改变时舍弃过期结果。播放中也观察进度；直连大视频十秒内推进不足五秒且仍有播放意图时，校验公网能否取得同一区间。若仍卡顿，保留播放位置和播放版本切换，一次失败的备用线路检查会推迟下一次检查。暂停、定位、离开和旧网络回调均有独立保护。

在这部 112.8 MiB 的试点视频上，单走 IPv6 的 HLS 一轮中，第一次观察到播放时间推进约需 25.04 秒；随后 64.55 秒内播放了 40 秒。自动选中公网的一轮中，首次观察到时间推进约需 19.28 秒；随后 64.91 秒内推进 65 秒，拖动后继续播放。第二轮确实读取了主清单和分片，并请求过 1080p 档位。短探测也曾选中随后变慢的直连，正是加入播放进度复查的依据。上述“首次推进”是 UI 自动化观测上界，并非按显示器帧测得的首帧时间。图库的同项测试保留手机已有缓存，不把缓存热度或读取首屏列表的时间当作链路带宽提升。
