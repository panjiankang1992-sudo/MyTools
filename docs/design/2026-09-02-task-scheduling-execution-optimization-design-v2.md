# 任务调度与执行服务优化设计（收敛版 v2）

## 1. 目标与边界

本轮优化只解决当前任务调度与执行链路的可靠性、可恢复性和可运维性，不建设通用工作流平台。

核心目标：

- Step 与 Complete 上报在网络抖动、进程重启后仍可可靠完成。
- Scheduler 通过租约、版本号和幂等约束避免重复执行与旧节点越权提交。
- Executor 启动时先恢复本地任务，再接收新任务。
- 调度、执行、业务调用使用统一协议、指标和结构化日志。
- 旧任务按业务逐个灰度迁移，任何阶段都能切回旧链路。

本轮明确不做：

- 通用 DAG、`task_dependency` 和可视化编排平台。
- 引入 MQ、工作流引擎或新的分布式协调组件。
- mTLS、短期 JWT、eBPF 或透明域名网关。
- DRAFT、PUBLISHED、RETIRED 等完整定义发布流程。
- 强制中断已经进入第三方 Provider 的请求。
- Scheduler 统一编排 Step 级重试。

## 2. 当前架构

```text
Business Service
      |
      | create / query / cancel / result
      v
Scheduler API ---- MySQL
      |
      | claim / heartbeat / step / complete
      v
Executor ---- local WAL ---- Script Release
      |
      +---- process / HTTP / domain service
```

职责保持简单：

- Scheduler：任务状态、租约、幂等、执行契约和节点选择的唯一事实源。
- Executor：领取任务、校验执行契约、运行步骤、本地持久化上报并在重启后恢复。
- 业务服务：创建和查询任务；迁移期保留旧执行路径作为回滚开关。

## 3. 必须保持的可靠性约束

### 3.1 上报幂等

- Step 与 Complete 都携带稳定幂等键。
- Executor 先写 WAL，再发起上报；收到成功或等价成功后才清理记录。
- Scheduler 使用数据库唯一约束和状态条件更新兜底，重复请求不重复产生副作用。

### 3.2 启动恢复

- Executor 启动顺序固定为：加载配置、扫描 WAL、恢复未完成上报、注册节点、开始 Claim。
- WAL 损坏记录进入隔离区并产生告警，不因单条坏记录阻塞全部启动。
- 恢复期间不领取新任务。

### 3.3 租约与防旧写

- Claim 产生租约和执行版本；Heartbeat 只能延长当前持有者的租约。
- Step 与 Complete 必须匹配任务、节点和执行版本。
- 租约失效后，旧 Executor 的上报不能覆盖新执行结果。

### 3.4 执行契约与发布物完整性

- Claim 返回定义 ID、版本和摘要，Executor 在运行前校验定义摘要。
- 脚本步骤携带发布物摘要，Executor 使用本地 package index 和文件内容计算结果校验。
- 不匹配时立即拒绝执行并上报明确错误，不尝试使用未知版本。

## 5. 仍然欠缺的内容

### 5.1 上线前必须完成

| 缺口 | 最小验收方式 | 完成标准 |
| --- | --- | --- |
| Linux 进程隔离验收 | 在目标 Linux 运行 Executor 条件测试 | 4 个跳过测试全部执行并通过，超时后无残留子进程 |
| 双 Scheduler 数据库验收 | 使用真实 MySQL 启动两个 Scheduler | 并发 Claim 唯一、租约接管正确、重复上报幂等、旧版本写入被拒绝、重启后状态一致 |
| Executor 生产形态启动验收 | 使用非 root 用户和真实目录启动 | package index 可读、WAL 可写、先恢复后注册、重启后待上报记录清零 |
| 监控与告警联调 | 接入真实 Prometheus/日志系统 | Journal/Outbox 积压、恢复失败、租约异常等既定告警可触发并恢复 |
| 配置与密钥核验 | 检查生产部署清单 | Scheduler、Executor、业务侧 token 独立，敏感文件权限为 `0600`，日志无密钥和敏感参数 |

### 5.2 按业务完成，不阻塞平台首发

1. 注册邮件先完成一次完整灰度和回滚演练。
2. 再迁移媒体目录、阅读搜索/缓存、视频与标签等旧任务。
3. 每个业务独立保留旧路径开关、对账指标和回滚说明。
4. 稳定观察后再删除旧定时器、旁路脚本和兼容代码。

### 5.3 暂缓项

- Step 重试继续由 Executor 进程内执行，现有秒级退避不需要新增 Scheduler 状态机。
- cgroup v2 仅在宿主机已提供 delegation 时启用，否则保留 `prlimit`。
- `bubblewrap` 仅用于无需联网的脚本；联网任务继续使用显式域服务 URL。
- 日志归档、长期报表和全量旧任务下线放到各业务迁移阶段。

只有出现以下证据时，才重新评估 Scheduler 编排 Step 重试：等待时间超过 30 秒、重试持续分钟级或小时级、进程内等待明显挤占并发槽位、需要跨节点接力或人工恢复。

## 6. 简化后的运行策略

### 6.1 重试

- 短暂错误：Executor 进程内有限重试。
- Executor 重启：通过 WAL 恢复上报，通过租约决定任务是否重新领取。
- 业务副作用：必须由业务幂等键保护，调度层不替代业务幂等。

### 6.2 资源与网络

- 默认使用进程组终止、超时和 `prlimit`。
- 只有确认宿主机支持时再启用 cgroup v2。
- 不建设透明网络沙箱；脚本仅访问配置中明确声明的服务地址。

### 6.3 回滚

- 平台升级：回滚 Scheduler/Executor 镜像，保留数据库和 WAL 数据。
- 业务迁移：切换到 LEGACY，并停止新链路创建；已经创建的任务继续查询或人工对账。
- 不通过删除任务数据实现回滚。

## 7. 完成定义

平台可靠性改造完成需要同时满足：

- Scheduler 与 Executor 全量自动化测试通过，平台差异测试在 Linux 通过。
- 真实 MySQL 双实例完成并发、重启、幂等、租约接管和 fencing 验收。
- Executor 以生产用户完成 WAL 恢复和脚本发布物校验。
- Prometheus 与结构化日志接入完成，关键告警至少演练一次。
- 至少一个业务完成 LEGACY 到 CANARY 再回滚或晋级的完整周期。

“所有旧任务迁移并删除旧链路”是后续业务治理目标，不与平台可靠性改造混为一个完成条件。
