## 2. 工程约定

- 新增 service/news-digest-service，Java 21、Spring Boot、Maven、MySQL/Flyway；不修改根 Maven 模块。
- 当前工作区已有大量其他任务改动，只修改本能力需要的文件，不重置、不回滚其他改动；共享文件修改前重新读取。
- 新 Java 包按 controller、Model、mapper、service、utils 及功能分包组织。public 方法有中文 Javadoc，配置/枚举/常量有类级中文注释，标识符与配置键使用英文。
- 新业务错误在 common/ErrorCode.java 管理，业务异常不硬编码消息。
- 本轮优先实现可确定性验证的规则、证据抽取和模型无关的数据链路；外部模型适配与真实调用单独验收，不能用标题补造详情。
- 源配置与真实发送默认关闭；测试采用本地固定材料和模拟渠道，自动化测试不得发真实消息。
- 源正文视为不可信输入；解析器限制 XML 实体、URL、响应体和耗时，渲染清洗 HTML。
- 对外 owner 由 Gateway 注入，不接受用户任意指定；内部管理接口和用户接口分开。
- MySQL 约束、并发与迁移需用真实 MySQL 验证；H2 通过只算快速回归证据。

## 6. 必须先解决的集成细节

### 6.1 执行节点与联网

当前 Executor README 表明：网络隔离开启时仅支持离线脚本，allowed-domains 尚不是已实现的透明域名代理。因此：

- 不能仅添加 allowed-domains 就宣称采集或定位脚本可用。
- 来源抓取优先由 News 服务受控抓取模块执行；执行器任务通过内部认证接口调度。
- 地区解析必须真正从指定 Executor 的出口环境执行，不能由 News 服务替代后仍标成 Executor 所在地。
- 需要联网的节点使用明确的部署网络策略；全局关闭隔离不是默认解决方式。
- 对隔离网络中的执行器，必须先提供受控本机代理/内部访问能力或选择已配置可联网的专用节点，再开展真实定位验收。

### 6.2 Messaging 兼容

现有通用 Provider 以邮件为主，QQ 是原消息回复 Provider；DeliveryService 仍验证 send_email 步骤。必须把新任务定义、fence、渠道 Provider 和请求版本作为一组交付，不能只加枚举。

旧纯文本邮件请求保持行为；HTML 和多渠道新契约明确 contentType。News 使用不透明 destinationId；真实地址及 Webhook 由 Messaging 管理。

### 6.3 详情与来源

前十详情不足时保持原排名并标记 DEGRADED；实时来源未准备时，仅固定材料通过的结果标为离线验证。接入模型前冻结供应商协议、模型、预算和可处理来源范围；模型不是来源授权的替代。

### 7.2 真实环境

按当前本地 SSH 配置解析目标、先验证连接；不使用飞书/UbuntuHermes 部署，不展示生产 Secret。先检查基础设施与实际版本，再运行隔离测试和仅采集的影子任务。

真实邮件/飞书/QQ 测试使用明确绑定的本人或指定测试目标；未绑定目标时不能猜收件人。供应商、账号、配额和模型费用未明确前只进行模拟验证，其他工程工作继续。

### 7.3 关闭条件

正常版满足四类各 20 个独立事件、前十完整详情；降级版必须显示实际数量和原因。三渠道各有独立真实发送证据；内容严重无依据断言为零、跨 owner 访问被拒绝、重复提交无多重逻辑发送。七日影子观察记录完整后，才可勾选 N26。
