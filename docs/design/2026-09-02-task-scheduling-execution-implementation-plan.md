## 3. 剩余实施阶段

### 阶段 A：冻结候选版本

目标：确认文档对应的代码可以作为验收基线。

任务：

- 运行 Scheduler、Executor、根工程和 Deploy 测试。
- 执行 Maven 打包并检查编译告警。
- 执行 `git diff --check`。
- 核对示例配置、部署配置与代码配置键一致。
- 记录构建版本、数据库迁移版本和脚本发布物摘要。

门禁：所有非平台条件测试通过，无新增编译告警，候选版本可重复构建。

### 阶段 B：Linux Executor 验收

目标：补齐当前开发机无法提供的进程隔离证据。

任务：

- 使用目标 Linux、Java 21 和生产一致的非 root 用户运行测试。
- 执行当前在 Darwin 跳过的 4 个条件测试。
- 验证正常退出、超时、强制终止和孙进程清理。
- 使用真实 WAL、脚本目录和 package index 完成一次重启恢复。
- 若宿主机已支持 cgroup v2 delegation，再验证 cgroup；否则记录使用 `prlimit`。

门禁：4 个条件测试全部通过；任务结束后无残留进程；WAL 在注册和 Claim 前恢复完成。

### 阶段 C：双 Scheduler 与真实 MySQL 验收

目标：验证依赖数据库并发语义的关键约束。

按顺序执行五组场景：

1. 两个 Scheduler 同时 Claim 同一批任务，确认单任务只有一个有效持有者。
2. 当前持有者停止 Heartbeat，确认租约过期后可被另一节点接管。
3. 重复发送相同 Step 与 Complete，确认只产生一次有效状态变化。
4. 接管后发送旧执行版本上报，确认被拒绝且不覆盖新结果。
5. 在 Claim、上报和 Outbox 投递期间分别重启实例，确认最终状态一致。

门禁：五组场景全部通过，数据库无重复有效执行记录，无丢失的最终状态和 Outbox 事件。

### 阶段 D：监控与生产配置验收

目标：保证上线后能发现、定位和处置故障。

任务：

- 接入 Prometheus 抓取和结构化日志采集。
- 演练既定 Journal/Outbox 积压、WAL 恢复失败、租约异常等告警。
- 核对 Scheduler、Executor 和业务调用方使用独立 token。
- 核对敏感配置文件权限为 `0600`，日志不输出 token、邮件正文或敏感参数。
- 形成值班检查项和最短回滚步骤。

门禁：关键指标可查询，告警能触发并恢复，配置核验清单完成。

### 阶段 E：注册邮件首个业务灰度

目标：通过一个真实业务证明新链路可用且可回滚。

任务：

1. 保持 LEGACY 为生产默认，确认旧路径无行为变化。
2. 启用 SHADOW 一个完整业务周期，只创建和对账，不造成重复发送。
3. 小比例启用 CANARY，观察创建成功率、最终成功率、延迟、重复发送和 Outbox 积压。
4. 执行一次 CANARY 到 LEGACY 的回滚演练并完成结果对账。
5. 指标稳定后再决定是否提升到 PRIMARY。

门禁：无重复邮件、无任务丢失、回滚有效、业务结果可对账。

## 4. 后续业务迁移顺序

注册邮件完成后，按以下顺序逐个迁移，不并行扩大故障面：

1. 媒体目录类任务。
2. 阅读搜索与缓存类任务。
3. 视频与标签类任务。
4. 其余低频旁路脚本和旧定时器。

每个业务都复用同一模板：LEGACY 基线、SHADOW 对账、小流量 CANARY、回滚演练、PRIMARY、稳定观察、删除旧路径。

## 5. 暂不实施与重新评估条件

以下内容不进入当前实施范围：

- 通用 DAG 与任务依赖表。
- MQ、工作流引擎和新的一致性中间件。
- mTLS、短期 JWT、eBPF 和透明网络网关。
- 完整任务定义发布生命周期。
- Provider 请求的强制中断。
- Scheduler 编排 Step 级重试。

Step 重试默认保留在 Executor 内。仅在出现任一条件时重新设计：

- 单次等待超过 30 秒。
- 重试持续分钟级或小时级。
- 等待明显占用 Executor 并发容量。
- 需要跨节点接力或人工审批后恢复。

## 6. 发布与回滚顺序

推荐顺序：

1. 执行数据库迁移并保持旧调用兼容。
2. 发布 Scheduler，确认存活、数据库和指标正常。
3. 发布少量 Executor，确认注册、恢复和 Claim 正常。
4. 扩容 Executor，但业务继续保持 LEGACY。
5. 按阶段 E 启动注册邮件灰度。

出现任务重复、状态不一致、持续积压或关键告警时：

- 立即停止提升流量并切回 LEGACY。
- 暂停新链路创建，不删除已有任务、WAL 或 Outbox 数据。
- 对已有任务完成查询、补偿或人工对账。
- 修复并重新通过对应阶段门禁后再恢复灰度。

## 7. 完成口径

平台可靠性改造完成：阶段 A 至 E 全部通过，且注册邮件至少完成一次可验证的灰度与回滚周期。

全量迁移完成：所有旧任务逐业务完成 PRIMARY 稳定观察，旧定时器、旁路脚本和兼容代码已经清理。

两个口径分别跟踪，避免因全量业务迁移拖延平台首发，也避免平台首发后遗漏旧链路治理。
